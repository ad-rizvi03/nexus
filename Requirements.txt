20. SECURITY, PRIVACY, AND DATA SAFETY
Security is required even for a single-user application.

Implement:
- Secure password hashing.
- Authentication and authorization.
- CSRF protection where applicable.
- Input validation.
- Ownership checks.
- Safe error responses.
- Secure cookie settings.
- Rate limiting or reasonable login-attempt protection.
- Secret management through environment variables or local configuration outside version control.
- Protection against SQL injection.
- Safe rendering of note content.
- Database backups and a documented restore process.
Do not expose the development database or backend directly to the public internet.

Do not commit real credentials to Git.

Do not log complete private notes, passwords, SMTP credentials, or sensitive request bodies.

If multiple accounts are supported, verify that one user cannot read, edit, or delete another user's records.
21. TESTING AND QUALITY ASSURANCE
Treat testing as part of every phase rather than postponing it until the end.
Backend testing
Write unit and integration tests for:
- Authentication.
- Task creation and updates.
- Task ownership.
- Status transitions.
- Due-date and time-zone handling.
- Recurring task generation.
- Reminder eligibility.
- Duplicate reminder prevention.
- Retry behavior.
- Learning progress.
- Goal calculations.
- Time logging.
- Daily review behavior.
- API validation.
- Database migrations.
Use JUnit 5, Mockito, and Spring Boot test support.
Frontend testing
Test:
- Form validation.
- Task status changes.
- Calendar navigation.
- Date selection.
- Search and filters.
- Loading states.
- Empty states.
- Error states.
- Responsive layouts.
- Keyboard navigation.
- Dialogs and confirmations.
- Dashboard calculations.
End-to-end testing
Use a free browser-testing tool such as Playwright if practical.

At minimum, verify these complete workflows:
1. Register and log in.
2. Create a task.
3. Add a note.
4. Schedule the task in the calendar.
5. Change its status to In Progress.
6. Complete the task.
7. Verify persistence after refresh.
8. Create a learning roadmap.
9. Complete a learning topic.
10. Configure a reminder and verify the email delivery workflow.
11. Review unfinished tasks at the end of the day.
12. Confirm that unauthorized users cannot access private resources.
Do not declare the application complete simply because it compiles.

23. HOW THE CODING AGENT MUST WORK
Follow this execution protocol throughout development.
1. Inspect the existing repository before changing anything.
2. If the repository is empty, scaffold the project using the specified stack.
3. Check installed versions and existing configuration.
4. Create a concise implementation plan for the current phase.
5. Implement the actual functionality, not just its visual appearance.
6. Run the relevant build and tests.
7. Fix errors before proceeding.
8. Verify the affected screens and workflows in a browser whenever browser automation is available.
9. Update documentation and database migrations.
10. Commit changes logically if Git is available.
11. Report completed work, tests performed, known limitations, and the next phase.
Do not ask for confirmation after every routine implementation decision.

Make reasonable, reversible technical decisions independently. Ask for clarification only when a genuinely consequential decision cannot be resolved safely from the requirements.

Do not skip testing because a feature looks correct.

Do not rewrite working modules unnecessarily.

Do not create a new technology stack without a concrete reason.

If a dependency is unavailable or requires payment, find a suitable free alternative and explain the trade-off.

If the current phase cannot be completed, report the exact blocker and finish all independent work that remains possible.
24. DEFINITION OF DONE
The project is complete only when all implemented features work together.

The finished application must:
- Start locally using documented commands.
- Use PostgreSQL for persistent data.
- Provide secure authentication.
- Support full task management.
- Display today's tasks correctly.
- Provide calendar scheduling.
- Save notes and knowledge resources.
- Deliver configured reminders when the local runtime permits.
- Support learning roadmaps and revision.
- Track goals, habits, focus sessions, and time logs.
- Produce reports from real persisted data.
- Handle invalid inputs and failures gracefully.
- Protect user-owned records.
- Pass relevant automated tests.
- Use the requested visual design consistently.
- Work on desktop and mobile.
- Have no mandatory paid services.
- Contain no fake functionality presented as complete.
- Include clear installation, configuration, backup, and recovery documentation.
Do not mark any feature complete until its main workflow has been implemented and verified.

Start with Phase 0. Inspect the reference website, establish the architecture and design system, and begin implementation. Do not attempt to build every phase in one untested code-generation pass.
